# AI Cyber Threat Detection System

An AI-based full-stack web application that **detects, classifies and responds to cyber threats in real time**.

| Goal | How it is done |
|---|---|
| **Detect** | ML models score every network flow and URL as it arrives |
| **Classify** | Network traffic → Normal / DoS / Probe / R2L (intrusion) / U2R (privilege escalation). URLs → Benign / Phishing / Malware. An IsolationForest flags *unknown* anomalies. |
| **Act in real time** | FastAPI pushes each alert over a WebSocket to the live React dashboard |
| **Protect** | High/Critical threats auto-block the source IP; later requests from it are dropped |

## Architecture

```
simulator/replay_traffic.py ──┐            ┌──► MySQL / SQLite (events, detections, alerts, blocklist)
URL Scanner (React) ──────────┤  HTTP      │
                              ▼            │
                    FastAPI  /api/analyze/* ──► scikit-learn models (joblib)
                              │
                              └── WebSocket /ws/alerts ──► React dashboard (live feed + charts)
```

| Layer | Tech |
|---|---|
| Frontend | React 18 (Vite), Recharts, HTML/CSS/JavaScript |
| Backend | FastAPI, Pydantic, SQLAlchemy, WebSockets |
| AI / ML | scikit-learn, NumPy, pandas |
| Database | MySQL (SQLite fallback for zero-setup development) |

## Project structure

```
backend/app/
  main.py               FastAPI app, CORS, startup (loads models, creates tables)
  config.py             settings from env vars
  schemas.py            request validation (IP format, 41 traffic features, URL)
  ml/traffic.py         NSL-KDD columns + attack → category mapping
  ml/url_features.py    17 explainable lexical URL features
  services/detector.py  runs the models, returns a Prediction
  services/response.py  severity rules, alerting, auto-block
  services/alert_bus.py WebSocket broadcast
  routers/              analyze, alerts + stats + ws, blocklist
backend/tests/          27 pytest tests (unit + API integration)
ml/train.py             trains/compares models, writes docs/model_report.md
simulator/              replays real test traffic to simulate a live network
frontend/src/           Dashboard, URL Scanner, Alerts, Blocklist pages
docs/                   model_report.md, mysql_schema.sql
```

## API

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/analyze/traffic` | Classify one network flow (41 NSL-KDD features + `source_ip`) |
| POST | `/api/analyze/url` | Classify a URL, returns indicators |
| GET | `/api/alerts?severity=&status=&source=` | Alert history |
| PATCH | `/api/alerts/{id}` | Change status (open / blocked / resolved) |
| GET | `/api/stats` | Counters, threats by type/severity, per-minute timeline |
| GET/POST/DELETE | `/api/blocklist` | Manage blocked IPs |
| WS | `/ws/alerts` | Live alert stream |

## Results

See [`docs/model_report.md`](docs/model_report.md) (regenerated by `ml/train.py`).

| Model | Dataset | Accuracy | Macro F1 |
|---|---|---|---|
| Logistic Regression (selected) | NSL-KDD `KDDTest+` (5 classes) | 0.790 | 0.603 |
| Decision Tree | NSL-KDD `KDDTest+` | 0.740 | 0.509 |
| Random Forest | NSL-KDD `KDDTest+` | 0.738 | 0.468 |
| Char n-gram + lexical Logistic Regression | Malicious URLs (420k) | 0.984 | 0.971 |

**Why Logistic Regression beat Random Forest:** `KDDTest+` deliberately contains 17 attack types that never appear in training. Tree models overfit the training attacks; the linear model generalises better to new ones. R2L/U2R recall stays low because they have very few training samples (995 and 52). This limitation is why the IsolationForest anomaly layer exists: it catches 62.7% of attacks while flagging only 2.3% of normal traffic.

## Datasets

- **NSL-KDD**, Canadian Institute for Cybersecurity (Tavallaee et al., 2009)
- **Malicious URLs**, [faizann24/Using-machine-learning-to-detect-malicious-URLs](https://github.com/faizann24/Using-machine-learning-to-detect-malicious-URLs) (good/bad labels). Malicious URLs are split into *Malware* (links to executables/archives) vs *Phishing* by an explainable rule.

## Limitations & future scope

- Traffic is replayed from a dataset rather than captured live; live capture (scapy / CICFlowMeter) would need a feature extractor matching the training features.
- Blocking is simulated in the database; a real deployment would push rules to a firewall (iptables / cloud WAF).
- No authentication on the dashboard: add login (JWT) and rate limiting before exposing it beyond localhost.
- Deep-learning models (LSTM on flows, CNN on URLs) and retraining on newer datasets (CIC-IDS2017, UNSW-NB15).
